# ТЗ: Веб-приложение мониторинга vLLM-сервера «LLM Metrics»

**Версия:** 0.2 (согласованное ТЗ)
**Дата:** 2026-07-10

## 1. Цель продукта

Одностраничное веб-приложение для мониторинга сервера с vLLM (1cat-vllm):
состояние модели и инференса, GPU, системы, расчёт стоимости эксплуатации
(токены + электричество) и просмотр логов — в едином интерфейсе, в разрезе
произвольных периодов времени.

Целевой пользователь: админ/разработчик, владеющий одним сервером с vLLM.
Доступ из локальной сети, авторизация не требуется.

### Референс стиля
Тёмная тема, иконки-сайбар слева, крупные KPI-карточки, «живой» график сверху
с индикатором частоты опроса, сетка карточек по GPU-картам
(мощность / ВРМ-бар / утилизация / температура). См. `/tmp/pi-clipboard-3888289c-f088-4f8e-b9f5-da9aeca0af4f.png`.

## 2. Решённые архитектурные решения (согласовано)

| Решение | Выбор |
|---|---|
| Сбор данных | **Собственный коллектор внутри приложения** (без Prometheus): опрос vLLM `/metrics`, NVML, psutil; своё хранилище |
| Стек | **Next.js (React + TS, Tailwind, shadcn/ui, uPlot)** + **FastAPI (Python 3.11+)** |
| Хранилище | **SQLite (WAL)** в MVP, схема совместимая с миграцией на Postgres |
| Логи | **Файлы логов** (+ docker logs как тип источника, конфигурируется) |
| Деплой | **Docker Compose** на том же сервере, LAN, без авторизации, UI на русском |

## 3. Архитектура

```
┌────────────────────────── Docker host (сервер с vLLM) ──────────────────────────┐
│                                                                                  │
│  vLLM (1cat-vllm) :8000 ──/metrics──┐                                            │
│  GPU (NVML: /dev/nvidia*) ──────────┼──► ┌─────────────────────────────┐         │
│  ОС (psutil, /proc) ────────────────┤    │  llm-metrics-api (FastAPI)   │         │
│  логи vLLM (файлы / docker logs) ───┘    │  · Collector (async pollers)│  :8100  │
│                                         │  · Cost engine               │         │
│  ┌───────────────────────┐              │  · Log indexer/tailer        │         │
│  │ llm-metrics-web       │──API/SSE────►│  · SQLite (raw + aggregate)  │         │
│  │ (Next.js), порт 3000  │              └─────────────────────────────┘         │
│  └───────────────────────┘                                                        │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1. Компоненты бэкенда (FastAPI)

1. **Collector** — набор асинхронных poller-ов (APScheduler / asyncio):
   - **vLLM poller** (`GET :8000/metrics`, парсинг Prometheus text format):
     интервал по умолчанию **5 с**, конфигурируется. При недоступности
     эндпоинта источник помечается `offline` (в UI — значок на вкладке).
   - **GPU poller** (pynvml, `/dev/nvidia*`): интервал **10 с**.
   - **System poller** (psutil): интервал **10 с**.
   - **Log poller** — tail файлов / `docker logs --follow` (через mounted
     `/var/run/docker.sock` либо хвост выгружаемого файла): интервал **1–2 с**.
   - Все poller-ы устойчивы к ошибкам: сбой источника не роняет сбор остальных.
2. **Storage** — SQLite, схема §4. Политика ретенции §5.3.
3. **Cost engine** — расчёт стоимости §6.
4. **API** — REST + SSE, §7.

### 3.2. Фронтенд (Next.js)

- App Router, SSR только для первого рендера; данные через fetch/SSE.
- Графики: **uPlot** (лёгкие, живые) + shadcn/ui для карт и контролов.
- **Live-режим**: SSE-поток (обновление раз в ~2 с) + переключатель периодов.
- Заголовок (как в референсе): селектор модели + статус (`готов / деградация / оффлайн`).
- Сайдбар-иконки: Модель, GPU, Система, Стоимость, Логи, Настройки.

### 3.3. Конфигурация приложения

YAML/JSON (`metrics.config`), мапится в контейнер:
```yaml
sources:
  vllm:
    url: http://127.0.0.1:8000
    metrics_path: /metrics
    poll_seconds: 5
    model_name: "Qwen3.6-27B"        # или брать из vllm:cache_config_info
  gpus:
    poll_seconds: 10
    visible: all                     # или [0,1]
  system:
    poll_seconds: 10
  logs:
    sources:
      - name: vllm
        type: file                   # file | docker
        path: /var/log/vllm/server.log
        # container: vllm
    poll_seconds: 1
storage:
  sqlite_path: /data/metrics.db
  retention:
    raw_hours: 168                   # 7 дней
    hourly_days: 180
    daily_days: null                 # безлимитно
cost:
  currency: USD                      # вся стоимость — в долларах
  electricity:
    rate_per_kwh_usd: 0.10           # тариф за электричество ($/кВт·ч)
    system_baseline_watts: 200       # базовое потребление системы (CPU/RAM/SSD), замер/оценка
  tokens:
    per_million_usd:                 # тарифы токенов — $/1M токенов
      prompt: 0.5
      completion: 1.5
alerts: (фаза 4)
  telegram_webhook: null
```

## 4. Модель данных (SQLite)

| Таблица | Назначение |
|---|---|
| `metric_samples(metric TEXT, ts INTEGER, value REAL, gpu INTEGER NULL, source TEXT, model TEXT)` | Сырые метрики; индекс `(metric, ts)`; партицирование по дням (раздельные файлы/таблицы) — лёгкая чистка по ретенции. `model` — имя модели, обслуживающей запросы на момент замера (из `vllm:cache_config_info` / `/v1/models`); для GPU/системных метрик NULL |
| `metric_hourly(metric, hour INTEGER, avg, min, max, p95, count)` | Часовая агрегация (для периодов дней/недель) |
| `metric_daily(metric, day INTEGER, avg, min, max, p95, sum, count)` | Суточная агрегация (для графиков месяца и стоимости) |
| `tokens(ts, prompt_tokens, completion_tokens, requests_finished)` | Диффы счётчиков vLLM за интервал (база для стоимости токенов) |
| `log_entries(id, ts INTEGER, level TEXT, line TEXT, source TEXT)` | Индекс логов (полный текст в `line`); index по `ts`, `level` |
| `settings(key TEXT, value JSON, updated_at)` | Изменяемые настройки (цены, baseline W) — редактируются из UI, пересчёт стоимости |
| `gpu_devices(id, name, total_mem_mib, pci_bus)` | Справочник GPU (автообнаружение) |

Агрегатор — фоновая задача: каждый час пишет `metric_hourly` + `tokens`-час,
каждые сутки — `metric_daily`. При запросе «месяц» фронт получает суточные
точки, «час» — сырые выборки.

## 5. Функциональные требования по вкладкам

### 5.1. Общие
- **Переключатель периода** (глобальный, в шапке): `Live`, `5м`, `1ч`, `24ч`,
  `7дн`, `30дн`, `произвольный` (date-range). Live = SSE, остальные — история.
- **Индикатор статуса источников** (vLLM/GPU/система: ок / оффлайн), как
  «готов — W» в референсе.
- Кнопки экспорта CSV по активному графику (фаза 4).
- Все временные значения — локальное время сервера, ч/з UTC в БД.

### 5.2. Вкладка «Модель» (vLLM)
KPI-карточки (текущие значения при Live / за выбранный период):
- **Running requests** (`vllm:num_requests_running`) и **Waiting requests** (`vllm:num_requests_waiting`) — отдельные KPI-карточки, всегда видны
- Запросы/с, генерация токенов/с (`rate(prompt_tokens_total)`, `rate(generation_tokens_total)`)
- TTFT p50/p95, TPOT p50/p95, e2e p95 (из histogram-ов vLLM; при истории —
  вычисление п95 из сырых точек или из агрегатов)
- KV cache usage (%, gauge), prefix cache hit rate (`hits/queries` за период)
- Preemptions (число за период), причины завершения (stop/length/abort, doughnut)
- Распределение длин prompt/generation (гистограммы)

Графики: time-to-first-token, TPOT/ITL, e2e latency, throughput (ток/с),
KV cache usage, queue, prefix cache hit rate — каждый в своём чарте с периодом.

**Отслеживание модели в истории:** все метрики vLLM хранятся с меткой `model`
(§4). В шапке вкладки «Модель» и на графиках отображается модель/модели,
обслуживавшие выбранный период: если в период произошла смена модели —
график размечается вертикальными линиями с подписью (сегментация), KPI-
карточки показывают разбивку по моделям. Это нужно, чтобы исторически было
понятно, какая модель генерировала какие данные.

> Замечание: p95 из Prometheus-histogram в истории реконструировать нельзя —
> хранить дополнительно собственные квантили из сырых значений, где они
> доступны (vLLM отдаёт только buckets), либо аппроксимировать из buckets
> (метод: интерполяция в bucket'ах). В ТЗ фиксируем: **p95 считается
> интерполяцией по buckets** — достаточно для операционного мониторинга.

### 5.3. Вкладка «GPU»
Верхний блок (как в референсе): суммарная мощность всех GPU (W) — живой график
последних ~2–5 мин в Live; суммарный VRAM (используемый / общий) с подписью.

Карточки по каждой GPU (сетка 2×N):
- Мощность, W (текущая / upper limit)
- VRAM bar (использовано / всего, GiB)
- Утилизация SM, %
- Температура, °C
- Частота SM и памяти, MHz
- Причина троттлинга (активные флаги NVML, подсветка красным)
- ECC errors (correctable/uncorrectable, счётчики за период)

Графики по каждой GPU (выбираются чекабоксами): power, util, vram, temp, clock.

### 5.4. Вкладка «Система»
- CPU: загрузка % (общая + по ядрам, график), load average, частота, steal
- RAM: использовано/свободно/кэш (stacked), swap; прогноз исчерпания при росте
- Диски: занятость % по mount-ам (бары), I/O read/write MB/s (графики), IOPS
- Сеть: rx/tx Mbps (график), ошибки
- PSI pressure (cpu/io/memory, 10s/60s/300s) — ранний сигнал деградации
- Топ-5 процессов по CPU и по RAM (таблица, Live)

### 5.5. Вкладка «Стоимость» ⭐ (ключевое отличие от Grafana)

**Источники расчёта:**
- Токены: `tokens`-таблица (диффы `prompt_tokens_total` /
  `generation_tokens_total`) × тарифы из `settings`.
- Электричество: `∫ P dt`, где `P = Σ(GPU power, W) + system_baseline_watts`
  (константа, редактируется в UI). Точность: минутные/часовые интегралы из
  сырых данных (7 дней), далее из `metric_hourly`.

**KPI-карточки:**
- Стоимость сегодня / за выбранный период (валюта из конфига), разбивка:
  токены / электричество (stacked bar)
- Стоимость за последний месяц + тренд (line, daily)
- Стоимость за 1k output-токенов (внутри: токены + электричество)
- Стоимость на запрос (avg)
- кВт·ч за период, средняя мощность (W)

**Графики:** стоимость/день (месяц), мощность/день (для сопоставления с
платой за электричество), кривая «стоимость-накопительная» за период.

**Редактирование тарифов** (в этой вкладке + Настройки): rate токенов
in/out per 1M ($), $/кВт·ч, baseline W. Изменение тарифов **пересчитывает
историю** (тарифы хранятся отдельно от данных — стоимость выводится на лету).

> Рекомендация (фаза 4): опциональный внешний источник мощности
> (PDU/розеточный счётчик: REST-API или MQTT) вместо константы baseline.

### 5.6. Вкладка «Логи»
- Таблица: время (точное до мс), уровень (INFO/WARNING/ERROR, цветные чипы),
  источник (vllm/...), текст.
- Фильтры: уровень (multi), текст (поиск по строке, LIKE + опц. инвертированный
  индекс), источник, **дата** (навигация по дням: «< 10.07 2026 >», клик по
  дате на календарной шкале).
- Сверху: мини-график «логи по уровням за день/неделю» (bar), кликабельный
  по дням → фильтрация.
- Режимы: **История** (страницы 100/250/500, глубина — пока хранится, §5.7)
  и **Live-хвост** (SSE, автопрокрутка, пауза по скроллу вверх).
- Кнопки: скачать выбранный диапазон (txt/csv), «копировать строку».
- Автопарсинг известных паттернов vLLM в боковую колонку: «140/140 · GPU KV
  cache 87.3% · prefix cache 12%» (regex по строкам stat-лога), счётчики
  ошибок за день.

**Ретенция логов:** индексируется/хранится настраиваемо, default 14 дней
(`log_retention_days`); при превышении — удаление древних `log_entries`
(оригинальные файлы не трогаем — храним копию/индекс).

### 5.7. Вкладка «Настройки»
- Тарифы (как в 5.5: токены $/1M, электричество $/кВт·ч), baseline W, модель (max context)
  (имя модели подхватывается автоматически из vLLM, редактируемое значение не требуется)
- Источники: URL vLLM, пути логов, интервалы опроса
- Ретенция, часовой пояс, валюта
- «Проверка источников» (ping vLLM/NVML/файлы логов) + версия vLLM
  (из `vllm:cache_config_info` / `/v1/models`)

## 6. Нормативы стоимости (формулы)

```
kWh(t)  = Σ (Σ_gpu P_gpu,i + P_base) * Δt / 3600 / 1000
C_tok   = (prompt_tokens * rate_in_usd + completion_tokens * rate_out_usd) / 1_000_000
C_elec  = kWh * rate_per_kwh_usd               # USD
C_total = C_elec + C_tok                       # USD, отображение в $
cost_per_1k_out_tok = C_total * 1000 / completion_tokens
cost_per_request    = C_total / requests_finished
```
Пересчёт истории при смене тарифов — без перехранения метрик (тариф =
отдельная сущность с `updated_at`; при запросе периода используются тарифы,
активные на момент периода — **версионирование тарифов** в `settings`).

## 7. API (FastAPI, 127.0.0.1:8100, наружу через Next.js rewrite)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/overview` | KPI шапки: статус источников, модель, текущие мощности/VRAM |
| GET | `/api/model?from&to` | Квантили/средние по метрикам vLLM + cause-of-finish breakdown |
| GET | `/api/metrics/{metric}?from&to&gpu` | Точки для графиков (downsampled) |
| GET | `/api/gpus?live` | Снимок всех GPU |
| GET | `/api/system?live` | Снимок системы + топ процессов |
| GET | `/api/cost?from&to` | Расчёт стоимости + разбивка + unit costs |
| GET | `/api/logs?from&to&level&query&source&offset&limit` | Страница логов |
| GET | `/api/logs/stats?from&to` | Подсчёт по дням/уровням |
| GET | `/api/live` (SSE) | Поток: vLLM+GPU+система (пачки раз в 2 с) + события логов |
| GET/PUT | `/api/settings/cost` | Тарифы (версионирование) |
| GET | `/api/health` | Живость бэка + статус poller-ов |

Next.js проксирует `/api/*` на бекенд (`rewrites`) — единый хост
`http://server:3000`.

## 8. Нефункциональные требования

1. **Нагрузка на сервер:** коллектор + БД ≤ ~200 МБ RAM, <3% CPU (1 ядро) в
   steady state. Опросы — неблокирующие, с дедлайнами.
2. **Отказоустойчивость:** падение vLLM/GPU-доступа не останавливает приложение;
   данные помечаются пропусками (в графике — разрыв, не 0).
3. **Производительность UI:** отрисовка серии ≤ 10k точек < 100 мс (uPlot);
   период «30дн» отдаёт ≤ 1500 точек (агрегаты).
4. **Безопасность:** бинд бэка на 127.0.0.1, наружу только фронт; CSRF не нужен
   (GET-only + PUT settings в LAN без аутфент — допустимо по ТЗ, зафиксировано).
5. **Бэкап:** `/data` (SQLite + конфиг) — ежедневный copy в `/backups` (7 копий).
6. **Логирование самого приложения:** stdout → файл, уровень INFO.
7. **Обновляемость:** миграции БД (alembic-совместимые SQL-схемы), версия в UI.

## 10. Допущения и открытые вопросы

1. **Одностек:** одна vLLM-инстанция, одна модель на сервере (селектор моделей в шапке структурно предусмотрен, scope = 1). Multi-GPU TP внутри одной модели поддерживается. **Модель отображается в метриках модели** с историческим отслеживанием смены (см. §5.2).

## Открытые вопросы — статус

Все вопросы закрыты: 1) тарифы токенов и электричества — в **$** (§3.3, курс валют не нужен), 2) baseline — настраиваемая константа, **200 W** по умолчанию, 3) глубина логов — **14 дней**, 4) имя приложения — **llm-metrics**, порт фронта **3000**.

### Исходные замечания

1. **vLLM V1-метрики** считаются базовым набором (`vllm:*`); точный список
   проверяется по `curl :8000/metrics` конкретной версии 1cat-vllm на этапе F0
   (метрики отличаются между релизами — коллектор делает маппинг «логическое
   имя метрики → список кандидатов имён», чтобы переживать апгрейды).
2. GPU: NVIDIA (NVML). Если в 1cat-vllm нестандартные GPU (например, в
   референсе V100-SXM2) — всё равно NVML, ок. Альтернатива (AMD/ROCm) — не
   в scope.
3. `system_baseline_watts` — настраиваемая константа (default **200 W**);
   PDU-метрирование — фаза 4.
4. Часовой пояс: время сервера.
5. Ретенция логов — 14 дней (§5.6).
